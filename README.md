# LAAW — Local AI Agent Workflow

LAAW is a workflow for local AI agents running on limited hardware. It targets models of 9b–35b with a 64k token context window, and structures the agent's work into small, reviewable, human-gated steps so a small model can reliably work on a codebase.

- **Plan before code.** Every task gets a plan file that you approve before implementation starts.
- **Human gates.** You approve the plan, the implementation, and the propagated context. The agent never skips a gate.
- **Deviations are recorded.** Anything that deviates from the approved plan is noted in the task's notes.
- **Context propagates.** What a task creates or changes is written back into the project's context files (a small wiki the agent reads before working).
- **Files stay small.** `.ai/` files over ~1500 words (≈ one read at the session's context budget) are split, so the agent only ever loads what it needs.

LAAW is not a project management solution — it is a workflow for the user to work with the agent. Tasks are done sequentially, not in parallel, by a single agent. The tasks folder is git-ignored for that reason, so tasks and IDs are unique per user. If you want parallel agents, give each agent its own git worktree and bootstrap the project in each one.

## Repository contents

| File | Purpose |
|---|---|
| `laaw/` | The LAAW CLI (Python package): owns task state, status transitions, dependencies, and the generated markdown views |
| `bin/laaw`, `bin/laaw.ps1` | Thin wrappers so `laaw` can be on PATH |
| `workflow.md` | Condensed workflow reference, read by the agent at the start of every session |
| `skills/` | The workflow skills: `plan-task`, `implement-task`, `propagate-context`; plus optional `bootstrap-project` and `gather-context` |

Requires Python 3. The CLI is invoked as `laaw` when a wrapper from `bin/` is on PATH, otherwise as `python -m laaw` with this checkout on your cwd or PYTHONPATH.

## Bootstrap a project

From this repository:

```sh
# Copy the workflow files into <project>/.ai/workflow/, create the
# .ai/tasks/ and .ai/context/ skeleton, and git-ignore .ai/tasks/
laaw sync workflow /path/to/project
# (path is optional — defaults to the current directory)
```

This creates:

```
project/
└── .ai/
    ├── workflow/workflow.md   # the agent's workflow reference
    ├── tasks/index.md         # empty task index (git-ignored)
    └── context/index.md       # empty context index
```

Task state starts empty: the CLI creates `tasks.json` on the first `laaw task register`, and every other file under `.ai/tasks/` (`tasks.md`, per-task `task.md` scaffolds, `notes.md`, subtask tables) is generated by the CLI from that state.

### Install the skills

```sh
# Copy the skills wherever your agent picks them up from
laaw sync skills /path/to/project/.agents/skills
# or, for a global installation:
laaw sync skills ~/.agents/skills
```

## Tell the agent about the workflow

For the workflow to actually be used, the agent needs to know to read `workflow.md`. `laaw sync workflow` does this for you: it creates or updates a `Workflow` section in the project's `AGENTS.md` (created if absent, appended if missing, left untouched if already there — re-running never duplicates it):

```markdown
## Workflow

This project uses LAAW. Before doing any task work, read
`.ai/workflow/workflow.md` and follow it. For planning, implementation, and
context propagation, use the `plan-task`, `implement-task`, and
`propagate-context` skills.
```

If you manage `AGENTS.md` by hand (or use a non-default layout), add that section yourself — see [Non-default install locations](#non-default-install-locations).

## Non-default install locations

`workflow.md` and the skills use the default locations as their vocabulary: they refer to `.ai/workflow/workflow.md`, `.ai/tasks/`, and `.ai/context/`, and expect the skills under `.agents/skills` (or `~/.agents/skills` for a global install). If you installed the workflow files or the skills somewhere else, the agent cannot discover that on its own — add the mapping to the `Workflow` section in `AGENTS.md`:

```markdown
LAAW locations in this project:
- workflow reference: `.ai/workflow/workflow.md` → `<actual>/workflow.md`
- tasks: `.ai/tasks/` → `<actual>/tasks/`
- context: `.ai/context/` → `<actual>/context/`
- skills: installed at `<actual>/skills/`
```

Any file a skill creates under `.ai/` (for example `gather-context`'s `.ai/.queue.md`) follows the same mapping.

Note: `laaw sync workflow` only creates the default `.ai/` layout; any other layout is set up by hand, which is exactly why the agent needs the mapping.

## How a task flows

1. **Plan** — you ask to plan a task. The agent registers it in state (`laaw task register`) and writes the plan file (`laaw task plan`). You iterate until the plan is good.
2. **Implement** — you ask to implement it. The CLI checks dependencies (`laaw task deps`), the agent implements, and you iterate until the implementation is good. Deviations from the plan are recorded as notes. You can abandon the task at any point; `laaw task cancel` marks it `cancelled`, and the CLI reports the tasks that depended on it, so you can decide what to do with them (cancel them too, re-plan, or replace the dependency).
3. **Propagate context** — the agent writes what the task created back into `.ai/context/` (or as tagged notes on the supertask, for subtasks). You approve it.

Task state lives in `.ai/tasks/tasks.json` — the source of truth, written only by the CLI. The markdown tables (`tasks.md`, each supertask's `subtasks.md`) and the notes files are generated from that state and are readonly: the model writes only `task.md` content and appends notes via the CLI.

Once a plan is approved it is frozen: only its Notes section (and the subtask table, for supertasks) can change. If a plan turns out to be unimplementable, you re-plan the whole task with the agent.

Big tasks become **supertasks**: one folder with a `task.md` and separate subtask folders, each planned and implemented one at a time (you can ask to plan several in advance). Subtask context lands as tagged notes on the supertask and is moved into the context files when all subtasks are done.

### Task statuses

Every task moves through: `not-planned` → `planning` → `in-progress` → `propagating-context` → `done`. A task can also be `cancelled` if you abandon it (terminal, like `done`). A task's dependencies must be `done` before it can be implemented.

## Git

- `.ai/tasks/` is git-ignored by default — plans are working documents, not repo content. `laaw sync workflow` adds the entry for you.
- `.ai/context/` **should be committed** — it is the project's documentation for agents, and sharing it means a fresh agent session (or another person's agent) starts with the right context.
